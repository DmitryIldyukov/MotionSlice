# MotionSlice — Контекст проекта для AI-агентов

## Что это

MotionSlice — образовательно-прикладная платформа с набором независимых AI-сервисов для контент-мейкеров.
Каждый сервис — отдельный AI-инструмент для конкретной задачи: обработать, преобразовать или сгенерировать контент.

Проект учебный, но строится по принципам production-разработки. Цель разработчика — освоить инженерию высоконагруженных систем через реальную практику.

## Целевая аудитория

Контент-мейкеры: авторы Telegram-каналов, YouTubers, стримеры, SMM-специалисты.

## Сервисы

**ArticleSlice** *(в разработке)*
Статья/текст на входе → ключевые тезисы → готовый пост для Telegram или других соцсетей.

**VideoSlice** *(идея)*
Длинное видео/стрим на входе → анализ аудио/видео → нарезка на короткие клипы с описаниями → скачивание.

**VideoGeneration** *(идея)*
Генерация видео с нуля по входным параметрам. Пример того, что не всегда нужен большой входной контент.

## Сервисы (полная карта)

| Сервис | Ответственность | Статус |
|---|---|---|
| **Auth Service** | Регистрация, логин, JWT, смена пароля | Планируется |
| **User Service** | Профиль, настройки, баланс пользователя | Планируется |
| **API Gateway** | Маршрутизация, валидация JWT, Feature Flags | Планируется с самого начала |
| **ArticleSlice** | Суммаризация статей → пост для соцсетей | В разработке |
| **VideoSlice** | Нарезка видео/стримов на клипы | Идея |
| **VideoGeneration** | Генерация видео с нуля | Идея |

## Архитектура

### Backend
- **Микросервисы** — каждый сервис изолирован, деплоится и масштабируется независимо
- **DDD** — агрегаты, сущности, доменные события, bounded context
- **Event-driven** — сервисы общаются через брокер (RabbitMQ / Kafka), не напрямую
- **Outbox Pattern** — гарантированная доставка событий
- **Saga Pattern** — распределённые транзакции между сервисами
- **API Gateway** — валидирует JWT один раз, остальные сервисы только читают claims из токена; отдаёт Feature Flags конфиг
- **Per-service database** — каждый сервис владеет своей БД (PostgreSQL)

### Frontend
- **Один React SPA** (монолит) с чёткой изоляцией каждого сервиса в отдельный модуль/папку
- В будущем — возможен переход на Micro-frontends (Module Federation), текущая структура это не усложняет
- **Feature Flags** — список сервисов и их статус приходит с бэкенда (API Gateway), фронтенд не хранит это состояние
- Статусы сервиса: `enabled: false` → вкладка скрыта; `status: "error"` → вкладка видна, показывается ошибка
- Это позволяет проводить тестирование на живых пользователях и поэтапно раскатывать новые сервисы

## Стек

| Слой | Технологии |
|---|---|
| Backend | C# / .NET (ASP.NET Core) |
| Frontend | React + TypeScript |
| Брокер | RabbitMQ или Apache Kafka |
| БД | PostgreSQL |
| Кэш | Redis |
| AI | OpenAI API / Anthropic Claude API |
| Прокси | Nginx |
| Контейнеры | Docker, Docker Compose |
| Observability | ELK Stack, Prometheus + Grafana |
| CI/CD | GitHub Actions |

## Цели разработчика

Разработчик изучает через этот проект:
- Проектирование микросервисной архитектуры
- DDD, Outbox, Saga и другие паттерны надёжности
- RabbitMQ / Kafka (топики, гарантии доставки, consumer groups)
- Observability: структурированное логирование, метрики, трейсинг
- C# / .NET углублённо (async/await, middleware, DI, EF Core)
- React + TypeScript
- Docker, Nginx, CI/CD
- Общие принципы Software Engineering для high-load систем

## Важно для агента

- Проект учебный, но код должен быть production-качества: паттерны, структура, надёжность
- Не упрощать архитектуру ради скорости — лучше сделать правильно и медленнее
- Сервисы должны быть независимы — избегать прямых зависимостей между ними
- Новые сервисы могут быть как processing (вход → трансформация), так и generation (генерация с нуля)
